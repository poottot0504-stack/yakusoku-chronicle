## ソースレビューで残るリスクと検証方針

### P0: 実環境E2Eが未検証

- 独立したSupabaseのステージング環境を用意した上で、そこでのみ `arena-ledger-staging-only.sql` と `arena-market-block-staging-only.sql` を適用する。
- ステージングのEdge Functionへ検証用フラグ・限定Originを設定し、認証済みのテストユーザーに限定して `profile → start → claim → profile → craft → enhance` を通す。
- 通常冒険・既存マーケットを壊さないこと、二重請求・複数タブ・失効したセッション・通信断を確認する。
- 本番DBに試験用テーブル・RPC・関数を作って代替しない。

### P1: ログイン・セーブスロットの端末間連携

- 闘技台帳はSupabase Authの `user.id` と `saveSlot` をキーにしている。
- `ensureYakusokuSession` はセッションがなければ匿名Authを発行する。別の端末で別Auth IDになる場合、同じゲーム利用者でも闘技財布が別になる。
- 既存 `yakusoku-account` の login/applySession によるユーザー切替、iPhoneとPC、5スロット、ログアウト・再ログイン・セーブ削除を実際に検証する。
- 必要なら、既存アカウントと闘技ウォレットのサーバー所有者紐付け・移管を実装する。単なるローカル保存の転送でコインを移さない。

### P1: 中断した試合・取引の復元

- 現在 `arenaSession` と `arenaPendingMutation` はメモリ上の状態。ページ再読み込みやアプリ終了で失われる。
- 戦闘結果の送信前に再読み込みすると未精算になり得る。生産成功後、プロフィール再取得前に中断した場合も、同じリクエストIDを確実に再送できるか未検証。
- 台帳の照会と安全な再試行・復旧導線を追加し、同一マッチ/リクエストの二重報酬を引き続き禁止する。

### P1: ゲームの公平性

- `start` のレスポンスが乱数seedをブラウザへ渡すため、クライアントで同じ戦闘を再現できる。Edgeのリプレイ検証は偽のコイン枚数を拒否できるが、**実際に手動操作した証明にはならない**。
- SQLは各ユーザー・スロット30試合/時を上限としているが、完全な自動周回抑止とは異なる。
- 公開前に「手動操作のみ」の公正さをどこまで保証するか決定する。必要ならサーバー逐次進行や不審な高速精算の監視などを設計し、プレイヤーに不利な誤検知を避ける。

### P2: 境界条件と実機

- iPhone Safari実機、PCブラウザ、アプリのバックグラウンド移行、並列タブ、二重タップ、100ターン境界、開始から1時間経過、ネットワーク断を確認する。
- 闘技コインをマーケットに出せないことを、既存マーケットEdge Functionと実際のDB制約を組み合わせて検証する。制約適用時は既存データに引っかからないか先に確認する。
